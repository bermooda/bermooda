# Internationalization (i18n)

How bermooda picks a locale per request, which message catalogs it loads, and how UI code translates strings. Source: [`app/core/i18n/`](../app/core/i18n/).

## Locale resolution

Storefront and admin resolve the locale differently. Both read the same `locale` cookie (one year, `SameSite=Lax`, written by `POST /api/set-locale`), and each ignores a cookie value it doesn't serve.

**Storefront**: `getRequestLocale(request)`, against the merchant's enabled locales (`locales` setting, Settings → Locales):

1. `locale` cookie
2. logged-in customer's `preferredLocale`
3. `Accept-Language`, negotiated over every range in `q` order (`es-ES, fr;q=0.8` picks `fr` when only `en`/`fr` are enabled); a region matches exactly (`pt-BR`) or by primary subtag (`de-CH` → `de`)
4. `defaultLocale` setting, else `en`, else the first enabled locale

The storefront layout calls `resolveLocale(request, headers)`, which also writes the cookie when it's missing.

**Admin**: `getAdminRequestLocale(request)`, against `ADMIN_AVAILABLE_LOCALES` (the locales with core catalogs), independent of the storefront's enabled locales. It never reads the customer session:

1. `locale` cookie
2. `Accept-Language`
3. `defaultLocale` setting, else `en`

`POST /api/set-locale` accepts storefront-enabled locales and admin locales, so the admin switcher in Settings → General works even when the storefront enables only `en`.

## Catalogs

`loadMessages(locale)` deep-merges, in this order:

1. core `en`, then active theme `en`, then each plugin in `pluginOrder ∩ enabledPlugins` `en`
2. for a non-`en` locale: core `<locale>`, then theme and plugin `<locale>` overlays

Missing keys fall back to English. Theme and plugin files live at `app/themes/<slug>/i18n/<locale>.json` and `app/plugins/<slug>/i18n/<locale>.json`; core catalogs are bundled into the SSR build. Extension files may use flat dotted keys or nested objects. A missing file is skipped. A file that isn't valid JSON or isn't a JSON object is logged and skipped, so one broken extension can't take down every page. `__proto__`, `constructor` and `prototype` keys are dropped.

Results are cached for five minutes under `i18n:<locale>` and `i18n:storefront:<locale>`. `setActiveTheme` and plugin enable/disable/order changes call `invalidateCachePrefix('i18n:')` (per process; see the multi-instance notes in [themes.md](themes.md) and [plugins.md](plugins.md)).

### Storefront scope

The storefront layout returns `loadStorefrontMessages(locale)`: the full catalog without the `admin` namespace (`admin.x` flat keys and a nested `admin` object). That data is serialized into every storefront document and every revalidation (after each cart action, for example). With the default theme this cuts the home page from ~143 KB to ~32 KB of HTML and each `.data` revalidation from ~111 KB to ~8 KB. Theme and plugin storefront strings must therefore not use `admin.` keys; plugin admin strings should.

Admin layouts (`admin/_layout`, `admin/public/_layout`) load the full `loadMessages(locale)`.

## Using translations

Layouts that load a catalog provide it with `useI18nValue`:

```jsx
const { locale, messages } = useLoaderData();
const i18n = useI18nValue(locale, messages);
return (
  <I18nContext.Provider value={i18n}>
    <Outlet />
  </I18nContext.Provider>
);
```

Components call `useT()` for `t(key, params?)` and `useLocale()` for the active locale. On the server, or anywhere outside React, use `translate(key, params, messages)`. Placeholders use `{name}`; an unknown key returns the key itself. There is no plural or ICU message support.

The root `Layout` sets `<html lang>` from the innermost layout whose loader returned `locale` and `messages`, so the attribute matches the rendered language (WCAG 3.1.1).

## Adding a locale

- **Storefront only:** add the tag to `LOCALE_OPTIONS` and `LOCALE_LABELS`, and ship `<locale>.json` in the theme (and any plugins). Merchants then enable it in Settings → Locales. Without a theme catalog, shoppers see English text.
- **Admin UI:** also add `app/core/i18n/messages/<locale>.json` with every key in `en.json` (`npm run check:i18n` enforces this in CI) and add the tag to `ADMIN_AVAILABLE_LOCALES`.
