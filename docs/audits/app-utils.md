# Audit: `app/utils/` (request helpers, rate limiter, cache, cookies, logger, secrets)

Audit date: 2026-10-11. Baseline commit: `765dc58` (bermooda 0.13.0).

Status: **open.** The first pass fixed the items under [Fixed in the audit PR](#fixed-in-the-audit-pr). The items under [Open](#open) are scoped for a later session; each has a location, the problem, and a proposed fix.

## Why this area

Picked at random from the areas the code-quality tracker didn't cover yet (`bootstrap/`, `app/emails`, `app/hooks`, `app/utils`, `setup/`). It's small (~500 lines of source), but almost everything depends on it: every storefront and admin request reads settings through the TTL cache, every auth, API, and webhook request goes through the rate limiter, and every absolute SEO URL comes from the request helpers. Following the request helpers turned up the two most serious findings: both trusted proxy headers that any client can send.

Verified non-issues:

- **`slugify`**: client-safe, NFD-normalized, only used by the product editor (the server re-validates slugs).
- **`secrets.server` IV/tag handling**: 12-byte random IV per encryption, GCM tag checked, format validated before decoding.
- **`serializeCookie` / `getCookie`**: covered by the storefront cookies audit; no new issues.
- **`getRequestOrigin` and a forged `Host`**: a request with a forged `Host` gets URLs on that host, but shared caches key on `Host`, so only the sender sees them. Canonicalizing unknown hosts is O5.

### Open

#### O1. Rate-limit keys still come from headers, not the socket (Medium, security)

- **Where:** `getClientIp` / `getClientKey`; `npm start` (`react-router-serve`), `Dockerfile`, `bermooda start`.
- **Problem:** `react-router-serve` doesn't pass the socket address to loaders or middleware, so the limiter can only use proxy headers. If the app is reachable without a proxy, or `TRUST_PROXY` is set higher than the real number of proxies, clients can still pick their own key. `TRUST_PROXY=0` avoids spoofing but puts every client in one bucket per endpoint.
- **Proposed fix:** add a small `server.js` that mounts `@react-router/express`'s `createRequestHandler` with a `getLoadContext` that stores `req.socket.remoteAddress` in a `RouterContextProvider` context. Use it in `npm start`, the Dockerfile, and `bermooda start`, and have `getClientIp` fall back to the socket address (and use it outright when `TRUST_PROXY=0`). The Vite dev server needs the same context (a Vite plugin or a dev-only fallback).

#### O2. Buckets are per raw pathname (Medium, security / scalability)

- **Where:** `enforceRateLimit` key `${policy}:${ip}:${pathname}`.
- **Problem:** `api-public` (120/min) and `api-admin` (300/min) apply separately to each concrete path, so a client spreading requests over `/api/v1/products/<slug>` or cart ids multiplies its budget by the number of paths it can name.
- **Proposed fix:** key on the matched route pattern rather than the concrete path (pass a pattern or route id into `rateLimitMiddleware`, or let each layout pass its own key). Keep per-endpoint buckets for `auth` so a busy `get-session` can't lock out `sign-in`. Add a route-level test that two slugs share one bucket.

#### O3. Rate limits and caches are per process (Medium, scalability)

- **Where:** `utils/rate-limit`, `utils/cache`.
- **Problem:** with more than one app instance (or Node cluster workers), every limit is multiplied by the number of instances, and a settings, theme, catalog, or i18n invalidation only clears the instance that handled the admin write. The others serve stale values for up to the 5-minute TTL.
- **Proposed fix:** either document single-instance deployment as a requirement (in `docs/postgres.md`, where multi-instance first becomes possible), or add a pluggable store: a DB-backed or Redis rate-limit counter and a cross-instance invalidation signal (for example a `cache_version` settings row checked once per request, or Postgres `LISTEN/NOTIFY`).

#### O4. Plugin secret key is a bare hash of `BETTER_AUTH_SECRET` (Low, security)

- **Where:** `deriveKey` in `secrets.server.js`.
- **Problem:** the AES key is `sha256(BETTER_AUTH_SECRET)`. It reuses the session-signing secret with no domain separation, and rotating that secret makes every stored plugin credential unreadable (U6 now explains the error, but there's no migration path).
- **Proposed fix:** add `enc:v2:` ciphertexts keyed with HKDF-SHA256 (`info: 'bermooda:plugin-secrets'`) from an optional dedicated `SECRETS_ENCRYPTION_KEY` (falling back to `BETTER_AUTH_SECRET`). Keep decrypting `v1`, re-encrypt on save, and add a CLI command that re-encrypts all plugin secrets from an old key to a new one.

#### O5. Unknown hosts get their own canonical URLs (Low, SEO)

- **Where:** `getRequestOrigin`, `buildCanonicalUrl` (`core/seo`).
- **Problem:** visiting the shop by IP address or through a stray DNS name produces canonical URLs on that host, which defeats the point of a canonical. The right origin is `baseUrl`, unless the host is an active sales-channel domain.
- **Proposed fix:** resolve the origin once per request (async, using the memoized `resolveChannelFromRequest`): `Host` when it equals the `baseUrl` host or the matched channel's `domain`, otherwise `baseUrl`. Pass it to the SEO builders from the storefront loaders instead of `request`, since `buildCanonicalUrl` and the JSON-LD builders are sync today.

#### O6. Email addresses in logs (Low, privacy)

- **Where:** `app/emails/job.server.js` (`Queueing password reset email to: ${email}`, abandoned-cart `{ email }`).
- **Problem:** customer and staff addresses end up in log storage. The password-reset one is inside the message string, so key-based redaction (U7) can't catch it.
- **Proposed fix:** log user, customer, or cart ids instead of addresses. Belongs with the `app/emails` audit.

#### O7. Color-mode cookie is written in four places (Low, maintainability)

- **Where:** `app/hooks/use-color-mode.jsx` (three `document.cookie` writes) and the inline script in `app/root.jsx`.
- **Problem:** the same `theme=…;path=/;max-age=31536000;SameSite=Lax` string is repeated, and none of the copies sets `Secure`, unlike the other preference cookies (K2).
- **Proposed fix:** one client-safe `buildColorModeCookie(mode)` in `#/utils/cookies`, used by the hook; the inline script keeps a literal copy (it can't import), with a test that the two match. Belongs with the `app/hooks` audit.
